kube-apiserver
 - Serve: exposes the Kubernetes REST API as the single entry point for every client (kubectl, controllers, scheduler, kubelets).
 - Secure: authenticates who is calling and authorizes whether they're allowed to do it via RBAC (identity extracted from client.crt, then identity -> role mapping happens).
 - Admit: runs admission controllers and schema validation to mutate or reject objects before they're accepted.
 - Persist: writes and reads cluster state in etcd, which no other component touches directly.
 - Notify: streams changes to watchers so controllers, schedulers and kubelets can react and reconcile

etcd
 - Distributed key-value store — etcd is a strongly consistent key-value database; multiple etcd instances use Raft to maintain a consistent state.
 - Stores cluster state — stores Kubernetes resources such as Deployments, Pods, Services, Secrets, ConfigMaps, and RBAC objects; built-in Kubernetes objects are typically stored as Protocol Buffers, while CRDs are stored as JSON.
 - Source of truth — etcd is the authoritative persistent state that the Kubernetes control plane reads and updates.

kube-controller-manager

Desired state → stored in etcd, primarily in the resource's spec.
Observed/recorded state → stored in etcd, primarily in the resource's status.
Controller → watches the API server for changes to spec and status, compares desired vs observed state, and reconciles the difference.

 - Bundle controllers: Runs many core Kubernetes controllers in a single process, such as Deployment, ReplicaSet, Job, Node, Namespace, and ServiceAccount controllers.
 - Reconcile workloads: Continuously compares the desired state with the observed cluster state and takes action to bring them in sync. For example, ensures a Deployment has the required number of Pods.
 - Monitor nodes: Watches node health and heartbeats, marks unhealthy nodes, and handles Pods on nodes that become unavailable.
 - Handle cluster bookkeeping: Performs tasks such as creating default ServiceAccounts, garbage-collecting objects, cleaning up namespaces, and maintaining EndpointSlices.
 - Leader election: Allows multiple kube-controller-manager instances for high availability, while ensuring only one instance actively runs the controllers at a time using a Lease.

kube-scheduler
 - Watch for unscheduled Pods: Watches the API Server for newly created Pods that don't have a node assigned yet.
 - Filter nodes: Eliminates nodes where the Pod cannot run based on constraints such as CPU/memory capacity, taints/tolerations, node selectors, affinity rules, and volume requirements.
 - Score remaining nodes: Ranks the nodes that passed filtering based on factors such as resource availability, affinity preferences, and spreading Pods across nodes.
 - Assign the Pod to a node: Selects the highest-scoring suitable node and records the node assignment for the Pod through the API Server.

kubelet
 - Run Pods — ensures Pods assigned to its node are created and running via the container runtime.
 - Monitor Pods — continuously checks container health and restarts containers when needed.
 - Report status — reports Pod and node health/status back to the API server.

kube-proxy
- Implements Service networking — makes a Kubernetes Service IP route traffic to the appropriate backend Pods.


types of Services

LoadBalancer: External LB LBIP:LBPort → NodeIP:NodePort → ClusterIP:ServicePort → Pod IP:PodPort

Readiness: after failureThreshold consecutive failures → Pod becomes NotReady → removed from Service traffic.
Liveness: after failureThreshold consecutive failures → kubelet kills and restarts the container.

a liveness failure does not directly set the Pod's Ready condition to False. Rather, the container restart and its resulting state prevent the Pod from being ready. Once the container restarts and passes its readiness checks, the Pod can become Ready again

Static Pod: A Pod managed directly by the kubelet on a specific node from a local Pod manifest, rather than by the Kubernetes control plane.
Used mainly for critical control-plane components (kube-apiserver, etcd, kube-scheduler, kube-controller-manager) that need to run during cluster bootstrap.

DaemonSet: A Kubernetes workload that ensures one instance of a Pod runs on every eligible node.

CNI
 - Every pod gets its own unique IP, and any pod can reach any other pod, on any node, directly by that IP without NAT. Kubernetes doesn't say how to achieve this. The CNI plugin decides.
 - Each node owns a block of pod IPs. When a pod starts, it gets an IP from its node's block, and every other node already has a route saying "that block lives on that node." So a new pod needs no routing update anywhere else
 - when a new pod starts:
    - Allocate an IP. It calls its IPAM, for example host-local, to reserve a free IP from this node's range.
    - Create a veth pair. It moves one end into the pod's network namespace and renames it eth0. The other end stays on the host, named something like veth… or cali….
    - Configure inside the pod. It assigns the IP to eth0, sets the MTU, brings the interface up, and adds a default route.
    - Configure on the host. It adds a route telling the host that traffic for the pod IP should go through the pod's host-side veth, e.g. 10.244.1.5 dev cali3f2a1b

Emissary pod:
 - diagd process (control plane / controller): Watches Kubernetes resources such as Listener, Host and Mapping, and generates configuration for Envoy.
 - envoy process (data plane): Uses that configuration to handle incoming requests and forward them to backend Services.

Emissary by default has following configuration:
 - HTTP: Service port 80 → Pod target port 8080
 - HTTPS: Service port 443 → Pod target port 8443

HPA

1. Deployment controller: Manages the rollout by deciding the desired replica counts for v1 (\(x\)) and v2 (\(y\)). It identifies v2 as the new ReplicaSet by comparing its Pod template with the Deployment's current Pod template. During a normal rolling update, it generally scales up v2 and scales down v1, subject to the rollout strategy and availability constraints.
2. ReplicaSet controllers: Each ReplicaSet controller ensures that the actual number of Pods matches its ReplicaSet's desired replica count. It creates or deletes Pods as needed.
3. HPA controller: Calculates CPU utilization across eligible Pods from both ReplicaSets, generally covering those \(x+y\) Pods, and adjusts the Deployment's desired total replica count. It does not decide which ReplicaSet to scale.
